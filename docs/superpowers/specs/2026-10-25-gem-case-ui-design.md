# Gem Case UI再設計案

状態: 2026-10-25にユーザーが実装を承認。会話で、右側パネルへの固執は不要、必要なら専用画面に変更してよいとの方針を確認した。本仕様に沿って実装・検証する。

## 目的と優先順位

Apotheosisの通常Gem Caseに近い「検索 → 種類選択 → 純度別の個数確認・取出 → 強化」を、一つの画面で行えるようにする。文字一覧と独立した加工viewを置き換える。優先順位は操作の一貫性、画面内への収まり、元画面に近い配置と外観の順。ユーザーは右側での完結を好むが、現状でも占有が大きいため、専用画面への変更を許容している。

## 方針の比較と今回の提案

| 案 | 利点 | 制約 |
| --- | --- | --- |
| 右側パネルを全面改修 | バッグ通常収納を直接操作できる | バッグ幅に専用UI幅が加算され、大型バッグや大きいGUI倍率で収まりにくい |
| 中央にGem Case専用表示を開く | バッグの大きさに関係なく一定の面積を使え、元画面の配置を再現しやすい | 通常収納の直接操作には戻る操作が必要 |
| 画面幅に応じて両方を提供 | 広い画面では同時表示できる | 二つの配置・入力処理・検収が必要で、切替による体験差も生じる |

今回の提案は中央の専用表示。右側には小さい「Gem Caseを開く」入口のみを置く。ユーザーは表示方法の選択を任せており、中央表示を選ぶ判断は実装側の提案である。二重のレイアウトは保守しない。

専用表示は既存のバッグメニュー上に重ねる方式を第一候補にする。Core 1.5.2.2343の公開JARに`StorageScreenBase.setModalOverlay(WidgetBase)`が存在することをjavapで確認した。別のサーバーメニューを開き直さず、現在のバッグ・upgrade・カーソル・sessionを維持する。背面のバッグを暗くし、クリック・スクロール・キー入力を背面へ流さない。

## 画面と操作

主画面176×230 GUI px、素材の張り出し56px、全体232×230 GUI pxを設計上の目標とする。これは実装側の寸法案で、装飾の微調整は任せるが、右側へ現状以上のパネル幅を追加しない。320×240のGUI座標領域に余白を含めて収まることを受け入れ条件にする。

```text
            ┌───────────────────────────┐
            │ 検索欄             戻る  │
┌─────────┐ │ ジェムアイコン6列×3行 設定│
│ 素材2×3 │ │ スクロール一覧        投入│
└─────────┘ │                           │
            │ 選択した種類の純度6段階   │
            │ 各強化先へのボタン5個     │
            │                     移動│
            ├───────────────────────────┤
            │ プレイヤーinventory 9×3   │
            │ hotbar 9枠                 │
            └───────────────────────────┘
```

- 上部に枠付き検索入力。種類の翻訳名とIDで検索し、右クリックで消去できる。検索入力中のinventoryキーを画面終了へ流さない。
- 種類は6列×3行のアイコングリッド、スクロールバーとホイールで移動する。全登録種類を扱い、所持ありを先、その中はID順とする。未所持は薄く描く。選択枠、合計所持数、ホバー時の名前を表示する。
- 選択した種類の6純度を一列に表示する。種類の最低純度より下は無効表示、所持0は薄いアイコン、所持数は保存数を表示し、ホバーで正確な数量を読める。表示用ItemStackの個数と保存数を混同しない。
- 取出は既存契約を維持する。左クリック1個、右クリック最大stack、Shift左クリックでプレイヤー通常inventoryへ移す。これは純正の全クリック挙動の再現より、既存の数量・投入契約の継続を優先する判断。
- その下に5個の強化ボタンを横並びに置き、各ボタンを対応する出力純度に結び付ける。種類を選び直す別の加工画面は廃止する。通常クリック1回、Shiftクリック最大64回を維持する。
- 強化ボタンの有効状態とホバー説明はサーバーの判断を使う。必要素材、Gem不足、素材不足、容量不足、同期中、保存ロックを区別する。
- 素材6枠は左に2列×3行で表示する。下位版では素材欄と加工操作を表示しない。素材の左右クリック・Shift移動を提供する。
- 下部にプレイヤーinventoryとhotbarを表示する。素材投入とGemの回収をこの画面で完結させる。通常バッグ収納は背面で直接操作させず、一括移動ボタンと「通常収納から素材補充」の設定を提供する。
- カーソル投入、一括移動、転送設定、素材補充、戻るは右端の小ボタンへ配置し、ホバー説明で用途と状態を示す。大きい文字ボタンの列を復活させない。
- 転送設定は専用表示内の設定ページへ移す。既存のDeposit／Restock、対象／除外、種類／純度フィルタを保ち、戻ると検索・選択・スクロールを復元する。設定ページ表示中は素材欄を操作不可にする。
- 戻るボタンとEscapeでバッグ画面へ戻る。外側クリックは専用表示を閉じるだけで、背面slotへのクリックやカーソルitemの投棄を起こさない。カーソルitemは保持する。

背景は茶色の収納面と暗色の外枠を使い、ジェム自身のアイコンを主役にする。独自の背景・枠・ボタン素材を用意し、Apotheosisの画像ファイルを本MODへコピーしない。右側の円形要素の再現や装備カテゴリフィルタの追加は今回の必須範囲に含めない。

## メニュー・同期と安全な更新

Gemの保存形式、32,767上限、素材の永続保存、既存の加工recipe・確定処理・通常収納優先順位・Pickup／Deposit／Restockの契約は維持する。ゲーム依存の画面・通信はneoforgeへ置き、coreへMinecraft型を入れない。commonからclient専用型を参照しない。

現在の加工previewは「種類＋一つの出力純度」に対する一件だけで、sessionも選択一件を保持する。5ボタンを同時表示するため、同じ種類の最大5強化先を一つの世代で取得する有界なpreviewへ改める。種類、menu ID、upgrade slot、session、revision、recipe世代に束縛し、古い種類・世代の応答で有効化しない。加工要求はクリックされた出力純度を明示し、サーバーでその出力のpreviewと現在のrecipe・素材・数量を再確認して確定する。既存の要求quota、byte予算と候補探索予算を迂回せず、種類を毎frame切り替えて五件のpreviewを要求する実装にしない。

素材編集可否は「Gemを選んだか」「その強化が成立するか」と分離する。空収納や無選択でも、正常に同期済みの素材を投入・回収できるようにする。素材・設定ロックと世代一致は引き続き要求する。Gem種類が存在しない場合も素材を閉じ込めない。

専用表示は既存の実slotを使い、素材やプレイヤーinventoryのコピーを独立した収納として扱わない。固定Coreのネイティブなslotクリック処理へ接続し、既存の予測・差分送信を維持する。必要なら対象版・用途を明記した小さいclient Mixin bridgeを設ける。公開overlay APIだけでネイティブslot操作が完結すると断定しない。drag配分、数字キー移動、double clickは実装計画時に固定版との接続を確認し、対応を実測して記録する。標準slotの左右クリックとShift移動は必須。

表示の終了、外側クリック、Escape、resize、設定ページへの切替、upgradeの差替え、バッグ無効化・切断で、素材の表示許可と座標を片付ける。背面のプレイヤーslotの座標を一時変更する場合は元へ戻す。Coreの標準overlay終了処理だけに依存せず、終了理由によらず同じ後処理へ接続する。メニューが無効なら専用表示から操作を継続しない。

未解決Gem ID／純度は保存を維持する。解決できないentryは警告付きの一覧からIDと数量を確認できるようにし、標準アイコンを作れないデータを黙って消さず、加工・取出を有効にしない。

## 検証と受け入れ条件

- 純度の数・順序、選択・検索・スクロール境界、所持0・未解決表示、previewの種類・世代照合に必要な意味のある単体テストを追加する。
- GameTestで5強化先previewと出力ごとの加工、旧世代／別種類拒否、無選択時の素材編集、表示終了後の素材操作拒否を検証する。既存の加工・材料・session・保存失敗回復テストも実行する。
- root check、翻訳datagen、生成resourceの追跡／未追跡差分、通常JAR内容検査、必須GameTestを実行する。UIだけの変更と見なして通信・slot境界の検証を省略しない。
- 固定NeoForge版JEI入り開発clientで、9列／12列バッグ、GUI座標320×240以上、resize、日本語／英語、検索中のキー、所持数表示、標準slotクリックとShift、強化の有効状態とコスト、設定往復、カーソル保持、外側クリック、背面入力遮断を確認する。
- 専用サーバー起動でclientクラス参照がないことを確認する。既存worldを上書きせず、新規／コピーで保存互換を確認する。
- ビルド成功、起動成功、画面の観測、実クリックによる検収を区別し、実施できなかった操作をdocs/verification.mdへ明記する。

## 対象ファイルと任せる判断

主対象はclient/GemCaseTab、GemCaseViewState、GemProcessingPanel、GemSettingsPanelとcache、menu/GemCaseContainer・GemProcessingActions、加工previewのnetworkコード、必要最小のclient Mixin、翻訳datagenと画面resource。確定処理・保存モデルは契約を変えず、必要な境界変更だけを行う。

具体的なclass分割、アイコン・装飾のpixel、preview DTOの構造とbyte上限の内訳、既存slot bridgeの実装詳細は実装計画へ任せる。中央表示が標準slot入力を安全に扱えないと固定版で判明した場合は、専用menuを増やす前に制約と差分を提示し、設計を更新する。
